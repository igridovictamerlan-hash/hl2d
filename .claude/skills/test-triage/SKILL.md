# Разбор упавших тестов

Большинство тестов поведения — это город на сиде, прокрученный N секунд, и проверка исхода. Любая правка, которая
меняет **порядок вызовов общей случайности** (`ctx.rng`) или карту, даёт другой ход событий — и часть таких
тестов падает, хотя ничего не сломано. А иногда падение — настоящая ошибка, которую замер не показал. Задача —
отличить одно от другого и не ослабить смысл теста.

## 1. Прогон и сводка

Полный `npm test` идёт ~12 минут — запускай в фоне с логом и жди циклом в одном вызове Bash (timeout до 600000):

```bash
npm test > /tmp/hl2d-test.log 2>&1 &
until grep -q "Test Files" /tmp/hl2d-test.log; do sleep 10; done
bash .claude/skills/test-triage/scripts/failures.sh /tmp/hl2d-test.log
```

Сводка — файл и имя теста, сообщение проверки, строка. Отдельный файл: `npx vitest run tests/<файл>.test.ts`,
отдельный тест: `-t "<часть имени>"`.

Два правила, на которых уже теряли время:

- **Пока идёт прогон, `src/` не трогать.** vitest импортирует файлы по мере запуска тестов — прогон смешает старый
  и новый код и покажет падения, которых нет. Нужно править — сначала останови прогон.
- **Останавливать — `bash .claude/skills/test-triage/scripts/stop-vitest.sh [фильтр]`**, не `pkill -f vitest`: в
  одной команде с `pkill` строка твоей оболочки тоже содержит «vitest», и она убивает сама себя (выход 144) вместе с
  чужими прогонами. Без фильтра скрипт останавливает **все** vitest машины (и долгий замер `world-audit` тоже); с
  фильтром — только прогоны, в команде которых он есть (`stop-vitest.sh "npm test"`, `stop-vitest.sh tests/dugout`,
  `stop-vitest.sh density`), вместе с их воркерами.

## 2. Воспроизвести

- Запусти падающий тест **один** (`-t`) и **весь его файл**. Тесты одного файла делят глобальное состояние: общую
  память фраз (`systems/phrases.ts` — от неё зависит выбор реплик и случайность), статические счётчики, объекты
  конфига, которые тесты правят через `Object.assign` (часть файлов восстанавливает их в `beforeEach`). Поэтому тест
  может проходить один и падать в полном файле — воспроизводи так, как он падал.
- `makeSim` сбрасывает номера CID (`resetCids`) — тест детерминирован при одинаковом коде и порядке. Если падение
  «плавает» между прогонами одного кода — ищи `Math.random`, время или порядок обхода `Map`/`Set` в своей правке.

## 3. Доказать причину

Не гадай по смыслу правки — откати подозреваемый кусок и прогони тот же тест:

```bash
cp src/ai/brains/CitizenBrain.ts /tmp/keep.ts      # сохранить
# временно убрать подозреваемое условие (sed или Edit), прогнать тест
npx vitest run tests/dugout.test.ts -t "разрушенный"
cp /tmp/keep.ts src/ai/brains/CitizenBrain.ts      # вернуть
```

Проходит без куска — причина в нём. Дальше вопрос «почему»: часто правка правильная, а сдвинулась случайность.

## 4. Трассировка

Вставь временную запись в сам тест и смотри, что происходит по ходу, а не только итог. Сохрани оригинал теста и
восстанови его после:

```ts
const OUT = '/tmp/trace.txt';
require('node:fs').writeFileSync(OUT, '');
sim.ctx.combat.deathListeners.push((c, k) => require('node:fs').appendFileSync(OUT, `${sim.ctx.time.toFixed(1)} погиб ${c.name} ${c.faction} ${(c.brain as any)?.mode ?? ''} от ${k?.name ?? '-'}\n`));
let tt = 0;
run(sim, 40, () => {
  if (++tt % 300) return;   // раз в 5 с
  require('node:fs').appendFileSync(OUT, `${tt / 60}s …счётчики, режимы мозгов, что проверяет тест…\n`);
});
```

Для сцен вне тестового файла — свой `.viz.ts` с `makeSim` по образцу `.claude/skills/world-audit/scripts/density.viz.ts`.

## 5. Решить

- **Ошибка в коде** — чини код (и это повод добавить проверку в свой тест). Пример: голодные стояли у закрытого
  магазина всю ночь — нашлось замером, а не тестом.
- **Хрупкая проверка** — исход верный, но проверка ловит случайный момент. Типично: «прокрутить ровно 40 с и
  проверить состояние», а в этот момент шёл законный переход (резервист ушёл на место погибшего, замена в пути).
  Чини проверку, сохраняя смысл: дождись условия (`until(sim, cond, secs)` — помощник в `tests/dugout.test.ts` — вместо `run` + `expect`), проверяй
  событие в окне, а не в точке. Не меняй сид, не убирай проверку, не ослабляй порог до бессмысленного.
- **Сравнительный тест** («новое лучше старого») — порог с запасом: падение на 2% от шума сида — признак, что
  метрика не различает; поменяй метрику на ту, что отражает суть (как в `tests/crowd.test.ts`).
- Чтобы падений было меньше заранее: новые системы в безголовых тестах выключены (`enabled = false`), а в
  выключенном виде правка не должна менять число и порядок вызовов `ctx.rng` — вызывай `rng.chance(…)` в тех же
  условиях, что и раньше (пример — `Families`: `!rich && rng.chance(…)`; `settleAll`: шанс `startHome` берётся до
  проверки «районы включены»). Своя случайность новой системы — `ctx.rng.fork(<число>)`.

## 6. Закрыть

После правок — прогнать изменённые файлы тестов, потом снова полный `npm run typecheck && npm test` (если `src/`
менялся после последнего полного прогона). В сообщении коммита — какой тест и почему изменён (хрупкая проверка
или другой исход), чтобы это не выглядело подгонкой.
